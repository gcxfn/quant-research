# GPU 因子计算引擎：建设计划包（2026-09-13，提案，未启动）

状态：**PROPOSED — 未获授权、未启动**。归属建议：T1（基础设施），不塞进 T3 本轮。
背景：T3 L0 批跑实测单 worker 约 30 秒/单元、峰值内存约 5GB、1482 个构造约 17 小时
（本机 20 逻辑核 / 15.6GB 内存）。

## 1. 目标与边界

**目标**：为"面板型因子计算 + 截面统计"建立 GPU 后端，把大规模因子评估从"小时级"
压到"分钟级"，支撑未来场景：分钟级（5m）因子扫描、10k+ 构造搜索、每日重估、
L2 路径依赖回测的批量化。

**不在目标内**：不改变因子语义与门槛口径；不用于 T3 本轮（本轮用云 CPU 多核即可）；
不引入 GPU 作为**唯一**路径（必须保留纯 Python 参考实现作为语义基准）。

**为什么不是"给现有代码加个 device=cuPy 就行"**：现有 bundle 是 Python 列表装盒浮点，
numpy 路径当初的 v1 正是死在"每个算子做 list↔ndarray 往返，实测比纯 Python 还慢"，
被整体重写为 v2（端到端数组）。GPU 若沿用列表 bundle，会比 numpy 更慢（往返代价更大）。

## 2. 现状与实测基线

| 项 | 实测值 | 来源 |
|---|---|---|
| 单单元求值 | 约 30 秒（numpy 路径） | 试跑 20 行：bundle≈13 分钟 + 20 单元≈11 分钟 |
| 单进程峰值内存 | 3.8–5.4 GB | 试跑/首片实测 |
| bundle 构建 | 约 13 分钟（5552 只 × 约1000 日 × 26 组字段） | 试跑与首片 |
| 本机 | 20 逻辑核 / 15.6GB RAM | 实测 |
| 现有后端 | 纯 Python（`operators.py` 305 行，语义基准）+ numpy（`operators_np.py` 843 行 + `stats_np.py` 164 行） | 代码 |
| 既有等价性成本 | 7 个测试文件 3272 行 + 4 个双路径探针 1051 行 | 代码统计 |
| 本机全量 L0 | 约 17 小时（分片串行） | 推定（首片 50 分钟） |

**结论**：瓶颈是"内存/单核串行"，不是 FLOPs。GPU 的价值在"把面板放进显存、把每单元
的 Python 循环变成批量张量运算"，但它必须与**列式 bundle** 一起做才算数。

## 3. 技术方案（四层）

1. **列式 bundle（必须有，且独立有价值）**
   - 面板改为 `float64` 二维数组：`field → ndarray[S, D]`（S=股票数，D=交易日数），
     缺值用 NaN；`close` 为轴锚；股票/日期索引表单独保存。
   - 内存估算：5552 × 1000 × 8B ≈ 44MB/字段 → 26 组字段 ≈ **1.1GB**（现在是 4–5GB，
     且是对象堆）。**只用 numpy 不做 GPU，也能把内存降到 ~1/4、bundle 构建大幅提速。**
   - 语义义务：与现有 `rows_by_symbol`/`StockRows.series` 逐位一致（缺行=NaN、轴=冻结
     交易日历、预热段截断、P1 掩码来源不变）。
2. **GPU 算子后端 `operators_gpu.py`**（torch 或 cupy，二选一，按可安装性定）
   - 15 个白名单算子 + 四则；滚动窗用 `unfold`/`as_strided` 或前缀和实现；
     `CS_RANK` 用排序+并列平均秩；`TS_RANK` 用窗口内比较计数（整数精确）。
3. **GPU 统计 `stats_gpu.py`**：月末截面 Spearman（排序法）、IC 衰减曲线（矩阵化）、
   十分位分层；bootstrap（1 万次 × 36 个月）保持 CPU（量小、且 RNG 身份敏感）。
4. **分派与缓存**：`compiler.evaluate` 增加第三路径（环境变量，如 `FACTOR_MINER_GPU`），
   CS_RANK 缓存按路径清理；默认不启用（与 numpy 路径同样的"默认关闭"策略）。

**数值确定性策略（硬要求）**：全部 `float64`；固定归约顺序（分段求和，禁用非确定性
原子加）；关闭 TF32/混合精度；提供 `--deterministic` 校验开关。即便如此，平台间仍存在
1e-12~1e-9 级差异 → 见 §6 的临界项回核协议。

## 4. 等价性审计清单（逐条，缺一不可）

与 `operators.py`（审计基准）逐位等价，以下语义**必须**在 GPU 路径复刻并用反例测试钉住
（括号内是历史缺陷，说明为什么不能想当然）：

1. None ↔ NaN 映射与传播；全窗 `min_periods=full`（窗口内任一缺失 → 输出缺失）。
2. ±inf 语义：仅 `ABS`/负号/`IF` 的**透传分支**原样输出 ±inf，其余算子把 ±inf 当非有限
   拒绝（numpy v1 曾把 ±inf→NaN，导致 `IF(cond,±X,Y)` 输出 None，被审出）。
3. 常数窗零方差：`max==min` 时 `STD`/`ZSCORE`/`CORR` 输出 None（B-01/P1 冻结规则）。
4. `STD` 为样本标准差（ddof=1）；`<2` 个有效值 → None。
5. `RET/DELTA` 偏移口径、越界 → None；除零 → None；`LOG(≤0)` → None。
6. `IF(cond,a,b)`：条件按**非零真值**（无比较运算符），条件缺失 → 缺失；三参等长契约。
7. 秩：`CS_RANK`/`TS_RANK` 并列取平均秩（`TS_RANK` 计数含自身、按 ≤ 计），
   掩码位置逐位一致（历史上"短序列静默补 None"与"i < len(vals) 兜底"都被堵死）。
8. 轴契约（wave2 TW-1/2/3）：常量标量/常量臂按该 symbol 的 PRICE `close` 轴长广播；
   引用字段而缺 `close` 轴 → `CompileError`；PRICE 字段缺失 → 同一 fail-closed 边界。
9. 稀疏字段（`lhb_net_buy`/`inst_net_buy`）部分覆盖 → 缺股票生成全 None 序列（D-32 协议）。
10. 常量公式（无字段引用）按调用方轴输出常量序列（AUDIT-1 常量臂缺陷）。

## 5. 工作分解与估算（单人，含审核）

| 阶段 | 内容 | 估算 |
|---|---|---|
| M0 可行性尖刀 | 单算子（`MEAN`/`STD`/`CORR`/`CS_RANK`）GPU 原型 + 与纯路径在小面板上的逐位对比 | 2–3 天 |
| M1 列式 bundle | `field → ndarray[S,D]` 构建 + 轴/掩码/预热语义对齐 + 内存与构建耗时实测 | 3–5 天 |
| M2 GPU 算子后端 | 15 算子 + 四则 + 缓存（约 800–1200 行） | 3–5 天 |

| M4 等价性测试 | 镜像 numpy 路径的测试套（约 3000+ 行）+ 反例（§4 十条） | 5–8 天 |

| M6 审核与身份修正 | 2–4 轮复审整改；新引擎身份 → 登记修正（旧 PASS 只覆盖旧身份） | 3–5 天 |
| **合计** | | **约 3–4 周（20–35 人日）** |

前置依赖：GPU 硬件（本地卡或云 GPU 机）；`torch`/`cupy` 版本固定并记录（依赖身份）。

## 6. 验收标准

1. §4 十条语义全部有反例测试；纯/numpy/GPU 三路径在同一输入上**要么逐位一致，要么
   差异落在登记带宽内**（建议 1e-9 相对）。
2. 真实数据零分歧探针：全池面板 + 至少 250 条覆盖各算子的公式，逐单元输出对比；
   分歧必须逐条定位到算子/顺序并解释。
3. **临界项回核协议**：任何 |月 RankIC| 距门槛 0.02 在 1e-6 内、或 bootstrap CI 端点距 0
   在 1e-6 内的候选，一律回**冻结的纯 Python 路径**复算，以纯路径结果为准。
4. 性能门槛：M0 后给出实测；若 GPU 端到端（含 bundle 构建 + 统计 + 落盘）不能把本批
   1482 构造压到 **≤1 小时**（本机或对标云机），则判定收益不足、**停止**（Go/No-Go 门）。
5. 不改变默认路径：不设环境变量时行为与现在逐字节一致；正式批仍必须从冻结快照运行。

## 7. 身份、治理与维护成本

- 新引擎＝**新身份**：`code_commit` + 依赖版本 + GPU 型号/驱动需入身份摘要；
  旧 PASS 只覆盖旧身份（沿用本仓一贯规则）。
- 三条路径（纯/numpy/GPU）**长期同步维护**：每次改算子白名单或语义都要三处实现 +
  三套测试。这是本计划最大的长期成本，必须在立项时被接受。
- 凭据/数据许可：GPU 机器上的数据仍受 `T1` 数据纪律约束；凭据不写仓库/日志。
- **本计划不自动启动**：需要用户明确授权（资源与工期都是用户决策）。

## 8. 风险与替代方案

| 风险 | 说明 | 缓解 |
|---|---|---|
| 端到端收益被 CPU 段吃掉 | bundle 构建、统计编排、JSON 落盘、门槛判定仍在 CPU | M1 列式 bundle 是收益前提；M0 后先做 Go/No-Go |
| 浮点平台漂移 | 临界候选翻转 | float64 + 确定性开关 + §6.3 回核协议 |
| 依赖与可移植性 | torch/cupy 版本、CUDA 驱动差异 | 版本固定在身份摘要；保留纯路径为唯一真理 |
| 维护三路径 | 每次语义变更三处同步 | 把"新增算子必须三路径 + 反例测试"写进引擎预登记 |
| 收益不足 | 分钟数据/更大规模的假设未验证 | 先用云 CPU 多核跑一轮做对照基线 |

**近期替代方案（推荐先做）**：云 CPU 大内存多核（32–64 核 / 256GB），用现有代码按分片
并行，1–2 小时出结果、零代码改动、零重新审计；同时可作为 GPU 立项的性能对照基线。

## 9. 决策门

- **G1（M0 后）**：单算子原型是否在等价性与加速比上同时达标？否则停止。
- **G2（M1 后）**：列式 bundle 是否把内存降到 ≤1.5GB、构建时间显著下降？
  （若列式本身已足够，可先只上 numpy 数组版，暂缓 GPU。）
- **G3（M3 后）**：端到端是否满足 §6.4 的 ≤1 小时？否则转为"仅分钟级场景专用"。
- **G4（M6）**：审核是否 PASS？未 PASS 不得用于正式批次。
